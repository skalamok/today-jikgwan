## 1. 요구사항 ID 체계

| 구분 | 형식 | ID 대역 | 대상 |
|---|---|---|---|
| 기능 요구사항 | REQ-F-nnn | 0xx | 회원 |
| | | 1xx | 경기 · 구장 정보 |
| | | 2xx | 직관 기록 |
| | | 3xx | 전적 집계 |
| | | 4xx | 관람 계획 |
| | | 5xx | 직관 메이트 |
| | | 6xx | 운영 · 데이터 관리 |
| | | 7xx | 온보딩 · 성장 |
| 비기능 요구사항 | REQ-NF-nnn | — | 성능 / 보안 / 호환성 / 신뢰성 |

중요도는 Must(필수) / Should(권장) / Could(선택)로 표기한다. 난이도는 상 / 중 / 하로 표기한다.

**추적성 표기.** 관련 화면 ID 열에는 해당 기능이 구현될 화면 ID 를 적고, 상세 설계가 작성된
화면은 디스크립션 NO 까지 함께 적는다(예: `SCR-AUTH-001 ①`). 반대 방향은 화면 설계서의
디스크립션 표에 매핑 요구사항 ID 열로 두어, 요구사항과 화면 요소를 양방향으로 대조할 수 있다.

## 3. 기능 요구사항

**수요자.** 요청 주체가 따로 있는 프로젝트가 아니다. 모든 요구사항의 수요자는 서비스를 쓸
야구 팬이고, 정의한 사람은 작성자 본인이다. 행마다 같은 값이 반복되므로 열로 두지 않았다.

**공수.** 난이도(상 · 중 · 하)로 갈음한다. 사람이 하나라 Man-Day 로 나눌 대상이 없다.
태스크 단위의 크기 추정은 프로젝트 목표 정의서 7.4 의 스토리 포인트에 있다.

## 6. 설계 쟁점 및 처리 결과

작성 과정에서 결정이 필요했던 항목과 그 결론이다.

| 번호 | 정해야 했던 것 | 어떻게 정했나 |
|---|---|---|
| 1 | 경기 데이터를 어디서 가져올 것인가 | **크롤링을 배제하고 운영자 등록으로 확보한다.** KBO 홈페이지 이용약관 제14조 차항이 자동화 수집과 타 플랫폼 연동을 금지하고, STATIZ 는 개인 이용자에게 제공할 수 있는 경로가 없음을 운영자 회신으로 확인했다. 실시간 스코어(REQ-F-105)는 데이터 이용 권한을 확보해야 가능하므로 조건부 기능으로 낮췄다. 확인 과정은 7장과 부록 A 에 있다 |
| 2 | 경기 결과를 누가 확정할 것인가 | **운영자만 등록·정정한다.** 스코어는 어디서든 확인할 수 있는 사실이라 사용자 입력으로 정할 이유가 없고, 한 경기가 잘못 확정되면 그 경기를 기록한 모든 사용자의 전적이 함께 틀어진다 (REQ-NF-015) |
| 3 | 승률을 몇 경기부터 표시할 것인가 | **통산은 1경기부터, 구장별 · 상대팀별 같은 차원별 집계는 5경기부터.** 통산은 "1경기 1승"처럼 모수가 함께 보여 오해가 적지만, 차원별은 여러 항목이 나란히 놓여 순위처럼 읽힌다. 기준값은 설정으로 조정할 수 있다 (REQ-F-305) |
| 4 | 전적을 어떻게 다시 계산할 것인가 | **전체 재계산.** 개인 관람 기록은 시즌당 수십 건이라 증분 반영의 이점보다 정합성이 중요하고, 경기 결과 정정처럼 과거 데이터가 바뀌는 경우도 같은 경로로 처리할 수 있다. 데이터가 커지면 증분으로 전환한다 (REQ-F-309) |
| 5 | 화면 24개 중 몇 개를 상세 설계할 것인가 | **7개.** 설계 판단이 들어간 화면을 골랐다. 선정 사유는 화면 설계서 "작성 범위"에 기재했다 |

미결로 남긴 항목은 하나다. 집계 재계산을 지금은 동기로 처리하는데, 경기 결과를 정정할 때
영향받는 사용자가 많아지면 응답이 지연될 수 있다. 사용자 수가 늘면 큐로 분리한다.

| 출처 | 결과 | 근거 |
|---|---|---|
| KBO 홈페이지 | **이용 불가** | 이용약관 제14조 차항이 자동화 수단을 통한 대량·반복 수집과 타 플랫폼 연동을 금지 |
| STATIZ | **이용 불가** | 운영자 회신 — 크롤링을 금지하며, 개인 이용자에게 제공할 수 있는 API 가 없다 |
| TheSportsDB | **이용 가능** | 이용약관이 공식 엔드포인트를 통한 수집·가공을 허용 |
| 기상청 (공공데이터포털) | **이용 가능** | 단기예보 · 기상특보 조회 서비스 활용 신청 승인 |

### 7.2 채택안 — 운영자 등록을 기본으로 두고 외부 API 로 보완

**경기 결과는 운영자만 등록·정정한다.** 스코어는 어디서든 확인할 수 있는 객관적 사실이므로
일반 사용자의 입력으로 정할 이유가 없고, 잘못 확정되면 그 경기를 기록한 모든 사용자의
전적이 함께 틀어진다.

| 상황 | 처리 | 요구사항 |
|---|---|---|
| 외부 API 에 결과가 있음 | 배치로 동기화해 확정 결과로 사용 | REQ-F-107 |
| 외부 API 에 결과가 없음 | 운영자가 직접 등록한다 | REQ-F-601 |
| 아직 등록되지 않음 | "확인 중" 으로 구분 표시하고 전적 집계에서 제외 | REQ-F-606 |

외부 데이터 경로는 아직 확정하지 않았다. 공식 API 이용과 자체 수집 중 어느 쪽을 택할지는
운영 시점의 이용 조건에 따라 정하며, 그때까지는 운영자 등록만으로 동작한다.
데이터 제공 인터페이스를 추상화해 둔 것은 이 선택을 뒤로 미루기 위해서다.

### 7.3 설계에 미치는 영향

| 항목 | 영향 |
|---|---|
| 경기 일정 · 결과 (REQ-F-101 ~ 103) | 운영자가 등록한다. 외부 API 를 도입하면 배치 동기화로 대체하되 등록 경로는 유지한다 |
| 팀 순위 (REQ-F-104) | 확정된 경기 결과로부터 직접 산출한다 |
| 실시간 스코어보드 (REQ-F-105) | 유료 구독이 전제이므로 화면 정의까지만 수행하는 조건부 기능으로 둔다 |
| 호출 한도 (REQ-NF-016) | 분당 30회 제한이 있어 화면 요청을 외부로 그대로 전달할 수 없다. 서버 배치 동기화와 캐시가 필수 설계 요소가 된다 |
| 관람 기록 · 전적 · 구역 만족도 | 영향 없다. 본래 사용자가 만드는 데이터다 |
