## 0. 프로젝트 요약

| 항목 | 내용 |
|---|---|
| **한 줄 정의** | 직관한 경기를 기록하면 그대로 **나만의 전적**이 되는 KBO 야구 관람 기록 서비스 |
| **해결하는 문제** | 티켓은 어딘가에 두고 잃어버린다. 사진은 갤러리에, 후기는 인스타에 흩어진다. **서로 이어지지 않아 시간이 지나면 언제 어느 구장에서 무슨 경기를 봤는지 떠오르지 않는다.** |
| **핵심 사용자** | 야구를 좋아하는 사람이면 누구나.<br>**자주 가는 팬** — 기록이 쌓여 나만의 전적이 된다.<br>**처음 가는 팬** — 그 기록이 좌석을 고를 때 참고가 된다. |
| **핵심 기능** | **① 직관 기록** — 경기 · 좌석 · 사진 · 비용 · 함께 간 사람을 한 번에 남긴다.<br>**② 나만의 전적** — 구장별 · 상대팀별 · 요일별 승패를 자동으로 집계한다.<br>**③ 좌석 고르기** — 실제 앉아 본 사람들이 남긴 구역 평가를 처음 가는 팬에게 보여준다.<br>**④ 직관 메이트** — 경기와 인원을 정해 글을 올리면 신청을 받아 **선착순으로 확정**한다. 확정된 사람끼리만 쓰는 대화방이 열리고, 경기가 끝나면 읽기 전용으로 바뀐다. 신고와 차단으로 원치 않는 상대를 걸러낸다.<br>**⑤ 관람 계획** — 가능한 요일 · 예산 · 구장 조건에 맞춰 시즌 일정을 짜 준다. |

| **본 프로젝트 범위** | 요구사항 정의서 · 화면 설계서 · 데이터 모델링 · API 명세 (구현·테스트·배포는 범위 외) |

## 1. 배경 및 문제 정의

KBO 리그를 현장에서 관람(직관)하는 팬은 경기 전후로 다음과 같은 불편을 겪는다.

- **기록이 흩어진다.** 티켓은 어딘가에 두고 잃어버린다. 사진은 갤러리에, 후기는 인스타에 흩어진다. 서로 이어지지 않아 시간이 지나면 언제 어느 구장에서 무슨 경기를 봤는지 떠오르지 않는다.
- **다녀와도 남는 게 없다.** 경기 결과는 어디서든 볼 수 있지만 누구에게나 똑같은 정보다. "내가 간 경기"만 골라낸 전적은 본인이 직접 세지 않으면 만들어지지 않는다. 팬들이 흔히 말하는 승요·패요(내가 가면 이긴다·진다)도 그래서 확인할 방법 없는 체감에 머문다.
- **처음 직관을 가거나 그 구장이 처음인 사람은 어느 자리가 즐기기 좋은지 모른다.** 어느 구역이 응원 소리가 잘 들리는지, 그늘이 지는지는 실제로 앉아 본 사람만 안다. 그 정보는 개인 후기나 커뮤니티 글에 흩어져 있어 구장별로 비교하기 어렵다.
- **관람 계획이 즉흥적이다.** 응원팀 홈경기 일정, 가능한 요일, 예산, 구장까지의 거리를 동시에 고려해 시즌 계획을 세우려면 일일이 손으로 맞춰 봐야 한다.
- **같이 갈 사람을 구하기 번거롭다.** 커뮤니티 글이나 오픈채팅으로 구하다 보니, 자리가 몇 개 남았는지 누가 확정됐는지를 글쓴이가 일일이 세어 답해야 한다. 약속이 어긋나도 기록이 남지 않는다.

## 2. 프로젝트 목표

**흩어진 직관 경험을 하나의 기록으로 모으고, 그 기록에서 개인 전적이라는 새로운 데이터를 만들어내는 서비스를 설계한다.**

세부 목표는 다음 다섯 가지다.

| 번호 | 목표 | 달성 판단 기준 |
|---|---|---|
| G-1 | 직관 기록을 한 곳에 모은다. | 경기 · 좌석 · 함께 간 사람 · 사진 · 비용 · 메모를 한 번의 작성으로 남길 수 있다. |
| G-2 | 기록이 쌓이면 전적이 되게 한다. | 응원팀 기준으로 승패가 자동 판정되고 구장별 · 상대팀별 · 요일별로 나뉘어 집계된다. 통산 승률은 첫 기록부터 보이며, 쪼갠 집계는 5경기가 쌓여야 승률을 보여준다. |
| G-3 | 시즌 관람 계획을 대신 짜 준다. | 목표 관람 횟수 · 가능한 요일 · 예산 · 갈 수 있는 구장을 입력하면 그 조건을 모두 만족하는 경기를 골라 일정으로 제시한다. 조건이 빡빡해 목표를 채우지 못하면 어떤 조건을 완화해야 하는지 함께 알린다. |
| G-4 | 쌓인 기록을 처음 가는 팬에게 되돌려준다. | 구역별 만족도가 그 구역에서 실제로 기록을 남긴 사용자의 평가만으로 산출되고, 구장 상세에서 좌석을 고를 때 보인다. |
| G-5 | 메이트를 구할 때 정원이 어긋나지 않게 한다. | 여러 명이 동시에 신청해도 정원을 넘겨 확정되지 않으며, 확정 순번이 중복되거나 비지 않는다. |

## 3. 대상 사용자

| 구분 | 어떤 사람인가 | 이 서비스에서 얻는 것 |
|---|---|---|
| 자주 가는 팬 (주 사용자) | 시즌에 여러 번 직관하는 사람 | 관람 기록이 쌓여 구장별 · 상대팀별 전적이 된다. 사진과 비용도 함께 보관되고, 시즌 관람 계획을 조건에 맞춰 편성할 수 있다. |
| 처음 가는 팬 | 직관 경험이 없거나 한두 번인 사람 | 앞선 사용자들이 남긴 구역 평가를 보고 좌석을 고를 수 있다. 첫 직관 가이드로 준비 과정을 확인한다. |

경기 데이터를 등록하고 결과를 정정하는 **운영자**는 서비스를 이용하는 사용자가 아니라 내부 역할이다. 필요한 기능은 REQ-F-6xx 로 별도 정의한다.

## 4. 수행 범위

### 4.1 In Scope (본 프로젝트 산출물)

- 요구사항 정의서 (기능 / 비기능)
- 화면 설계서 (와이어프레임 + 디스크립션 + 예외 처리 정책)
- 데이터 모델링 (ERD)
- API 명세 (OpenAPI 3.x)
- 발표 자료

### 4.2 Out of Scope

- 프론트엔드 · 백엔드 개발, 테스트, 배포

### 4.3 MVP 와 확장 범위

설계는 전체를 그렸지만 한 번에 만들지 않는다. **먼저 만드는 것은 "기록하면 전적이 된다"는
한 줄이 성립하는 데 필요한 것뿐이다.**

| 구분 | 요구사항 | API | 내용 |
|---|---|---|---|
| **MVP** | 33 | 27 | 가입 · 로그인 · 응원팀 설정 / 경기와 구장 조회 / 기록 작성 · 조회 · 수정 · 사진 / 통산 · 구장별 · 상대팀별 전적 / 구역 만족도 / 운영자 경기 등록 · 정정 |
| **확장** | 46 | 30 | 소셜 로그인 · 날씨 · 팀 순위 · 구단 채널 / 함께 간 사람 · 비용 · 평점 기록 / 요일별 전적 · 연승 / 직관 메이트 / 관람 계획 편성 / 배지 · 알림 |

아래 기능은 빠져도 기록을 남기고 전적을 보는 데 문제가 없다.

| MVP 제외 기능 | 확장으로 미룬 이유 |
|---|---|
| 소셜 로그인 | 이메일 로그인으로 가입과 인증이 된다 |
| 날씨 · 팀 순위 · 구단 채널 | 다른 서비스에서도 볼 수 있는 정보다 |
| 함께 간 사람 · 비용 · 평점 기록 | 없어도 승패 판정과 전적 집계에 지장이 없다 |
| 직관 메이트 · 관람 계획 | 기록이 쌓인 뒤에야 쓸모가 생긴다 |
| 배지 · 알림 | 사용을 북돋는 장치이지 기록 자체는 아니다 |

구역 만족도(REQ-F-110)만 MVP 에 남겼다. 다른 서비스에서도 볼 수 있는 정보가 아니라
이 서비스에 쌓인 기록에서만 나오는 값이고, 처음 가는 팬이 좌석을 고를 때 쓰는 것도 이것이다.

### 7.1 수행 방법론 — 폭포수 기반, 설계 반복 허용

| 구분 | 적용 |

#### 7.1.1 설계가 끝나면 애자일로 전환한다

설계 단계에서 폭포수가 맞았던 이유는 **만들 것이 이미 정해져 있었기 때문**이다.
산출물과 마감이 고정되어 있었고 요구사항도 직접 정했으므로, 단계마다 끊어 확정하는
편이 빨랐다.

개발 단계는 조건이 다르다. **설계만으로는 알 수 없고 만들어 봐야 드러나는 문제**가 있다.
이번 설계 검증 구현에서도 화면을 붙이고 나서야 발견한 것이 세 건이다(7.1). 단계를 끊어
두면 이런 문제가 다음 단계에 가서야 드러나므로, 짧은 주기로 만들고 확인하는 편이 낫다.

| 구분 | 전환 후 |
|---|---|
| 주기 | 1주 스프린트 |
| 백로그 | 7.4 의 에픽 · 태스크를 그대로 백로그로 쓴다 |
| 스프린트 목표 | MVP 태스크를 SP 순서가 아니라 **의존 관계 순서**로 담는다 (7.5) |
| 완료 기준 | 화면에서 동작이 확인되고 정합성 검사를 통과한 상태 |
| 요구사항 변경 | 스프린트 경계에서만 받는다. 진행 중 변경은 다음 스프린트로 미룬다 |

MVP 는 69 SP 로 확장(116 SP)의 절반이 조금 넘는다. 먼저 이만큼을 스프린트에 담고, 확장은
그 뒤 스프린트에서 우선순위를 다시 매겨 담는다.

되돌아간 실제 사례는 다음과 같다.

| 발견 시점 | 무엇이 드러났나 | 되돌아가 고친 것 |
|---|---|---|
| 요구사항 작성 중 | KBO 이용약관이 자동 수집을 금지 | 데이터 확보 방식을 크롤링에서 운영자 등록으로 전환 (v0.2) |
| 설계 검증 구현 중 | 화면이 응원팀을 보낼 때 팀 ID 가 필요한데 API 가 이름만 반환 | API 명세에 `homeTeamId` · `awayTeamId` 추가 |

| 사진 업로드에 따른 개인정보 노출 | 위치 정보 유출 | 업로드 시 EXIF 위치 메타데이터 제거를 비기능 요구사항으로 명시 |

## 9. 용어 정의

| 용어 | 정의 |
|---|---|
| 직관 | 경기를 중계가 아닌 경기장 현장에서 직접 관람하는 것 |
| 관람 기록 | 사용자가 직관한 경기 1건에 대해 남기는 기록 단위 |
| 개인 전적 | 사용자가 관람한 경기만을 대상으로 산출한 승·무·패 및 파생 지표 |
| 승요 · 패요 | 특정 인물이 관람하면 응원팀이 이긴다/진다는 팬 사이의 통칭 |
| 직관 메이트 | 같은 경기를 함께 보기로 한 다른 사용자. 줄여서 메이트라고 쓴다 |
| 함께 간 사람 | 기록에 남기는, 그 경기를 같이 본 사람. 서비스 회원일 수도 아닐 수도 있어 이름만 적을 수 있다. 모집으로 만나는 직관 메이트와는 다르다 (REQ-F-209) |
