|---|---|
| **한 줄 정의** | 직관한 경기를 기록하면 그대로 **나만의 전적**이 되는 KBO 야구 관람 기록 서비스 |
| **해결하는 문제** | 티켓은 서랍에, 사진은 갤러리에, 후기는 인스타에 남는다. **서로 이어지지 않아 시간이 지나면 언제 어느 구장에서 무슨 경기를 봤는지 떠오르지 않는다.** |
| **핵심 사용자** | 야구를 좋아하는 사람이면 누구나. 자주 가는 팬에게는 전적이 쌓이고, 처음 가는 팬에게는 그 기록이 **좌석을 고를 때 참고**가 된다. |
| **핵심 기능** | **① 직관 기록** — 경기 · 좌석 · 사진 · 비용 · 동행자를 한 번에 남긴다.<br>**② 나만의 전적** — 구장별 · 상대팀별 · 요일별 승패를 자동으로 집계한다.<br>**③ 좌석 정보 환원** — 실제 앉아 본 사람들의 구역 평가를 처음 가는 팬에게 보여준다.<br>**④ 동행 모집** — 경기와 인원을 정해 글을 올리면 신청을 받아 **선착순으로 확정**한다. 확정된 사람끼리만 쓰는 대화방이 열리고, 경기가 끝나면 읽기 전용으로 바뀐다. 신고와 차단으로 원치 않는 상대를 걸러낸다.<br>**⑤ 관람 계획** — 가능한 요일 · 예산 · 구장 조건에 맞춰 시즌 일정을 짜 준다. |
| **차별점** | **원천이 다르다** — 경기 결과는 어디에나 있지만 "내가 그 자리에 있었다"는 사실은 나만 안다. 이 서비스의 원 데이터는 남이 만든 경기 기록이 아니라 사용자가 남긴 그 사실이다.<br>**후기를 쓸 자격이 다르다** — 구역 평가는 그 구역에서 실제로 관람 기록을 남긴 사람만 작성할 수 있다. 가 보지 않은 사람의 평이 섞이지 않으므로, 처음 가는 팬이 좌석을 고를 때 근거로 삼을 수 있다.<br>**숫자를 함부로 만들지 않는다** — 2경기 2승을 승률 1.000으로 보여주지 않는다. 표본이 5경기 미만인 항목은 승률을 산출하지 않고 "표본 부족"으로 표시한다.<br>**쓸수록 정확해진다** — 자주 가는 팬이 남긴 기록이 처음 가는 팬의 좌석 정보가 되고, 그 팬이 다시 기록을 남기며 표본이 두꺼워진다. |
| **본 프로젝트 범위** | 요구사항 정의서 · 화면 설계서 · 데이터 모델링 · API 명세 (구현·테스트·배포는 범위 외) |

## 1. 배경 및 문제 정의

KBO 리그를 현장에서 관람(직관)하는 팬은 경기 종료 후 다음과 같은 상태에 놓인다.

- **기록이 흩어진다.** 티켓은 서랍에, 사진은 갤러리에, 그날의 감상은 인스타에 남는다. 세 가지가 서로 연결되지 않고 한데 모아 둘 곳도 없어, 시간이 지나면 "언제 어느 구장에서 무슨 경기를 봤는지"가 기억나지 않는다.
- **누적 데이터가 만들어지지 않는다.** 개별 경기 결과는 어디서든 조회할 수 있지만, 거기서 "내가 직접 간 경기"만 골라내 전적으로 만들려면 본인이 직접 세는 수밖에 없다. 팬 사이에서 흔히 이야기되는 승요/패요(내가 가면 이긴다/진다)도 그래서 확인할 방법이 없는 체감에 머문다.
- **관람 계획이 즉흥적이다.** 응원팀 홈경기 일정, 본인의 가능한 요일, 예산, 구장까지의 이동 시간을 동시에 고려해 시즌 관람 계획을 세우려면 수작업이 필요하다.
- **동행 구하기가 불편하다.** 같이 갈 사람을 구하는 과정은 커뮤니티 게시글이나 단체 대화방에 흩어져 있어, 누가 확정되었는지 관리되지 않는다.

> [보완 필요] 위 문제 인식은 서비스 기획 관점의 정성적 정의이다. 발표 자료에는 KBO 연간 관중 수 등 공개된 통계를 출처와 함께 인용해 문제의 규모를 보강할 것. 출처가 확인되지 않은 수치는 기재하지 않는다.

## 2. 프로젝트 목표

**흩어진 직관 경험을 하나의 기록으로 모으고, 그 기록에서 개인 전적이라는 새로운 데이터를 만들어내는 서비스를 설계한다.**

세부 목표는 다음 네 가지다.

| 번호 | 목표 | 달성 판단 기준 |
|---|---|---|
| G-1 | 직관 기록을 한 곳에 축적한다. | 하나의 관람 기록에 경기 정보, 좌석, 동행자, 사진, 메모가 함께 저장된다. |
| G-2 | 기록에서 개인 전적을 산출한다. | 구장별·상대팀별·요일별 승률과 연승 기록이 자동 집계된다. |
| G-3 | 관람 계획 수립을 자동화한다. | 사용자 제약 조건을 입력하면 시즌 관람 후보 일정이 자동 편성된다. |
| G-4 | 동행 모집을 관리 가능한 형태로 만든다. | 모집 정원과 확정 인원이 시스템에서 관리되고, 중복 확정이 발생하지 않는다. |

## 4. 핵심 차별점

기존 서비스는 **경기 데이터를 보여주는 것**에 집중한다. 본 서비스는 **사용자가 직접 만든 관람 데이터를 축적하고 파생 지표를 산출하는 것**에 집중한다. 경기 정보 조회는 기록 작성을 돕는 보조 기능으로 위치시킨다.

## 7. 시스템 구성 개요 (설계 전제)

| 구분 | 내용 |

## 8. 주요 설계 쟁점

본 서비스에서 단순 CRUD로 해결되지 않는 지점이며, 요구사항 정의서와 API 명세에서 상세히 다룬다.

| 쟁점 | 내용 |
|---|---|
| 전적 집계 방식 | 관람 기록이 추가·수정되거나 경기 결과가 정정될 때 누적 전적을 전체 재계산할 것인지 증분 반영할 것인지 |
| 소표본 승률 표현 | 관람 2경기 2승을 승률 100%로 표시하면 오해를 유발한다. 최소 표본 기준과 표시 정책이 필요하다 |
| 동행 선착순 확정 | 다수 지원이 동시에 발생할 때 정원 초과 확정을 방지하고, 동일 사용자가 같은 시각 다른 경기에 확정되어 있는지 검증해야 한다 |
| 관람 계획 편성 | 가능 요일, 예산 상한, 이동 시간, 응원팀 홈경기 여부를 동시에 만족하는 후보 일정을 선정해야 한다 |
| 경기 결과 정정 | 우천 노게임, 서스펜디드 등으로 결과가 변경되면 이미 산출된 개인 전적에 영향을 준다. 변경 이력 보존이 필요하다 |
