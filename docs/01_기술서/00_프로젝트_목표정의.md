## 1. 배경 및 문제 정의

KBO 리그를 현장에서 관람(직관)하는 팬은 경기 종료 후 다음과 같은 상태에 놓인다.

- **기록이 흩어진다.** 티켓은 어딘가에 두고 잃어버린다. 사진은 갤러리에, 후기는 인스타에 흩어진다. 서로 이어지지 않아 시간이 지나면 언제 어느 구장에서 무슨 경기를 봤는지 떠오르지 않는다.
- **가도 남는 것이 없다.** 경기 결과는 어디서든 볼 수 있지만 그것은 모두에게 같은 정보다. "내가 간 경기"만 골라낸 전적은 본인이 직접 세지 않으면 만들어지지 않는다. 팬들이 흔히 말하는 승요·패요(내가 가면 이긴다·진다)도 그래서 확인할 방법 없는 체감에 머문다.
- **처음 가는 사람은 좌석을 고를 근거가 없다.** 어느 구역이 응원 소리가 잘 들리는지, 그늘이 지는지는 실제로 앉아 본 사람만 안다. 그 정보는 개인 후기나 커뮤니티 글에 흩어져 있어 구장별로 비교하기 어렵다.
- **관람 계획이 즉흥적이다.** 응원팀 홈경기 일정, 가능한 요일, 예산, 구장까지의 거리를 동시에 고려해 시즌 계획을 세우려면 일일이 손으로 맞춰 봐야 한다.
- **동행 구하기가 불편하다.** 같이 갈 사람을 구하는 과정이 커뮤니티 게시글과 단체 대화방에 흩어져 있어, 누가 확정됐고 자리가 몇 개 남았는지 아무도 관리하지 않는다.

## 2. 프로젝트 목표

**흩어진 직관 경험을 하나의 기록으로 모으고, 그 기록에서 개인 전적이라는 새로운 데이터를 만들어내는 서비스를 설계한다.**

세부 목표는 다음 네 가지다.

| 번호 | 목표 | 달성 판단 기준 |
|---|---|---|
| G-1 | 직관 기록을 한 곳에 모은다. | 경기 · 좌석 · 동행자 · 사진 · 비용 · 메모를 한 번의 작성으로 남길 수 있다. |
| G-2 | 기록이 쌓이면 전적이 되게 한다. | 응원팀 기준으로 승패가 자동 판정되고, 구장별 · 상대팀별 · 요일별로 나뉘어 집계된다. 표본이 5경기 미만인 항목은 승률 대신 "표본 부족"을 표시한다. |
| G-3 | 시즌 관람 계획을 대신 짜 준다. | 목표 관람 횟수 · 가능한 요일 · 예산 · 갈 수 있는 구장을 입력하면 그 조건을 모두 만족하는 경기를 골라 일정으로 제시한다. 조건이 빡빡해 목표를 채우지 못하면 어떤 조건을 완화해야 하는지 함께 알린다. |
| G-4 | 동행 모집에서 정원이 어긋나지 않게 한다. | 여러 명이 동시에 신청해도 정원을 넘겨 확정되지 않으며, 확정 순번이 중복되거나 비지 않는다. |

## 3. 대상 사용자

| 구분 | 어떤 사람인가 | 이 서비스에서 얻는 것 |
|---|---|---|
| 자주 가는 팬 (주 사용자) | 시즌에 여러 번 직관하는 사람 | 관람 기록이 쌓여 구장별 · 상대팀별 전적이 된다. 사진과 비용도 함께 보관되고, 시즌 관람 계획을 조건에 맞춰 편성할 수 있다. |
| 처음 가는 팬 | 직관 경험이 없거나 한두 번인 사람 | 앞선 사용자들이 남긴 구역 평가를 보고 좌석을 고를 수 있다. 첫 직관 가이드로 준비 과정을 확인한다. |

경기 데이터를 등록하고 결과를 정정하는 **운영자**는 서비스를 이용하는 사용자가 아니라 내부 역할이다. 필요한 기능은 REQ-F-6xx 로 별도 정의한다.

## 4. 수행 범위

### 4.1 In Scope (본 프로젝트 산출물)

- 요구사항 정의서 (기능 / 비기능)
- 화면 설계서 (와이어프레임 + 디스크립션 + 예외 처리 정책)
- 데이터 모델링 (ERD)
- API 명세 (OpenAPI 3.x)
- 발표 자료

### 4.2 Out of Scope

- 실제 구현(프론트엔드·백엔드 코딩), 테스트, 배포 — 미니프로젝트 수행 범위 외

아래는 일정 문제로 미룬 것이 아니라 **외부 권리나 제휴 없이는 만들 수 없어** 제외한다.

| 제외 기능 | 이유 |
|---|---|
| 실시간 중계 · 문자 중계 | 중계권이 필요하다 |
| 티켓 예매 · 결제 연동 | 구단 및 예매처와의 제휴, 결제 대행 계약이 전제다 |
| 좌석 단위 실시간 잔여석 조회 | 예매 시스템 연동이 전제다 |

## 5. 주요 기능 그룹

| 그룹 | 기능 개요 | 요구사항 ID 대역 |
|---|---|---|
| 회원 | 회원가입, 약관 동의, 로그인·로그아웃, 응원팀 설정, 프로필 관리 | REQ-F-0xx |
| 경기 정보 | 경기 일정·결과 조회, 구장 정보, 구장 날씨, 구단 공식 채널 | REQ-F-1xx |
| 직관 기록 | 기록 작성·수정·삭제, 사진 업로드, 좌석·비용·메모 기록 | REQ-F-2xx |
| 전적 집계 | 개인 통산 전적, 구장별·상대팀별·요일별 집계, 연승 기록 | REQ-F-3xx |
| 관람 계획 | 제약 조건 입력, 후보 일정 자동 편성, 계획 확정 | REQ-F-4xx |
| 동행 | 모집 등록·지원·선착순 확정·취소, 문의 댓글, 확정자 대화방, 신고·차단 | REQ-F-5xx |
| 운영 | 경기 데이터 등록, 결과 정정 및 재집계 | REQ-F-6xx |

## 6. 시스템 구성

| 구분 | 내용 |
|---|---|
| 클라이언트 | Vue 3 기반 웹. 모바일을 기본으로 설계하고 900px 이상에서 데스크톱 레이아웃으로 전환한다 |
| 서버 | Spring Boot 기반 REST API |
| 인증 | 이메일 로그인, 소셜 로그인(구글 · 네이버 · 카카오). JWT 액세스 토큰 발급 |

| 파일 저장 | 이미지 원본과 썸네일을 별도 저장. 업로드 시 위치 메타데이터 제거 |
| 외부 경기 데이터 | 운영자 등록과 사용자 제보의 이중 구조. 데이터 제공 인터페이스로 추상화해 정식 소스가 확보되면 어댑터 교체로 대응한다 (요구사항 정의서 7장) |

## 7. 리스크 및 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| KBO 경기 데이터의 공식 공개 API 부재 | 실제 구현 시 데이터 확보 불가 | 데이터 제공 인터페이스로 추상화해 소스를 교체할 수 있도록 설계한다. 이용 가부를 확인한 결과 운영자 등록과 사용자 제보의 이중 구조를 채택했다(요구사항 정의서 7장). |

| 사진 업로드에 따른 개인정보 노출 | 위치 정보 유출 | 업로드 시 EXIF 위치 메타데이터 제거를 비기능 요구사항으로 명시 |

## 8. 용어 정의

| 용어 | 정의 |
|---|---|
| 직관 | 경기를 중계가 아닌 경기장 현장에서 직접 관람하는 것 |
| 관람 기록 | 사용자가 직관한 경기 1건에 대해 남기는 기록 단위 |
| 개인 전적 | 사용자가 관람한 경기만을 대상으로 산출한 승·무·패 및 파생 지표 |
| 승요 · 패요 | 특정 인물이 관람하면 응원팀이 이긴다/진다는 팬 사이의 통칭 |
| 동행 | 같은 경기를 함께 관람하기로 한 다른 사용자 |
