## 1. 테이블 구성

총 30개 테이블을 9개 도메인으로 구성한다.

| 도메인 | 테이블 | 역할 |
|---|---|---|
| 회원 | users, user_social_accounts, auth_tokens, user_team_history | 인증, 프로필, 응원팀 이력 |
| 경기·구장 | teams, stadiums, stadium_zones, games, game_weather, game_result_reports, game_revisions | 경기 데이터, 날씨, 제보 및 정정 이력 |
| 직관 기록 | attendance_logs, attendance_photos, attendance_companions | **서비스 핵심 원천 데이터** |
| 집계 | user_stats, user_streaks, zone_stats | 사전 집계 결과 |
| 성장 | badges, user_badges | 마일스톤 |
| 동행 | companion_posts, companion_applications, companion_comments, companion_messages, companion_message_reads | 선착순 확정 및 소통 |
| 안전 | reports, user_blocks | 신고 · 차단 |
| 계획 | viewing_plans, viewing_plan_stadiums, viewing_plan_items | 제약조건 편성 |
| 알림 | notifications | 정정·확정·배지 안내 |

## 2. 주요 설계 결정

### 2.1 중복 기록 방지 — attendance_logs

`(user_id, game_id)` 에 유니크 제약을 건다. 한 사람이 같은 경기를 두 번 관람할 수는 없으므로 데이터베이스 차원에서 막는다(REQ-F-201). 애플리케이션 검증만으로는 동시 요청 시 중복이 생길 수 있다.

### 2.2 중립 관람 표현 — cheer_team_id NULL

별도의 `is_neutral` 플래그를 두지 않고 `cheer_team_id`를 nullable로 둔다. 플래그와 팀 ID를 함께 두면 "중립인데 팀이 지정된" 모순 상태가 만들어질 수 있다. NULL 하나로 표현하면 그 상태가 존재할 수 없다.

승패 판정은 다음과 같다.

```
cheer_team_id IS NULL                  → 집계 제외
cheer_team_id = 이긴 팀                 → 승
cheer_team_id = 진 팀                   → 패
home_score = away_score                → 무
```

### 2.3 집계 테이블 분리 — user_stats

전적을 조회할 때마다 `attendance_logs` 전체를 집계하면 기록이 쌓일수록 느려진다(REQ-N-003). 차원(dimension)과 키(dimension_key)로 일반화한 사전 집계 테이블을 둔다.

| dimension | dimension_key | 예 |
|---|---|---|
| TOTAL | 'ALL' | 통산 전적 |
| STADIUM | 구장 ID | 잠실 전적 |
| OPPONENT | 팀 ID | 롯데 상대 전적 |
| DAY_OF_WEEK | 'SAT' | 토요일 전적 |
| SEASON | 시즌 연도 | 2026 시즌 |

차원별로 테이블을 따로 만들지 않은 이유는, 새로운 집계 축이 생길 때마다 테이블과 API가 늘어나는 것을 피하기 위해서다. `season_year = 0` 을 통산으로 약속해 시즌별/통산을 한 테이블에서 다룬다.

### 2.4 재계산 트리거 — REQ-F-309

집계 테이블을 두면 원천과 어긋날 수 있다. 다음 세 경우에 재계산한다.

| 발생 | 영향 범위 |
|---|---|
| 기록 생성·수정·삭제 | 해당 사용자의 관련 차원만 |
| 경기 결과 정정 | 그 경기를 기록한 **모든** 사용자 |
| 응원팀 변경 | 이미 작성된 기록에는 소급하지 않는다 |

세 번째가 중요하다. 응원팀을 바꿨다고 과거 기록의 승패가 뒤집히면 사용자가 납득하지 못한다. 기록 시점의 `cheer_team_id`를 기록마다 저장해두었기 때문에 프로필 변경과 무관하게 과거 판정이 유지된다. `user_team_history`는 이 판단의 근거를 남기기 위한 것이다.

### 2.5 정정 이력 — game_revisions

경기 결과는 개인 전적과 직결되므로 변경 전후 값, 사유, 변경자, 시각을 추가 전용으로 남긴다(REQ-F-603). 이 테이블은 UPDATE와 DELETE를 하지 않는다. `games` 테이블만 보면 "지금 값"은 알 수 있지만 "왜 바뀌었는지"는 알 수 없다.

### 2.6 동시성 — companion_posts

`confirmed_count`가 `capacity`를 넘지 않아야 한다(REQ-F-504, REQ-N-011). 애플리케이션에서 조회 후 증가시키는 방식은 동시 요청에서 깨진다. 두 가지 방법을 고려했다.

| 방법 | 처리 |
|---|---|
| 낙관적 락 | `version` 컬럼으로 갱신 충돌을 감지하고 실패 시 409 응답 |
| 비관적 락 | 확정 시 게시글 행을 잠그고 정원을 검사 |

경합 빈도가 높지 않으므로 낙관적 락을 기본으로 하되, `version` 컬럼을 두어 두 방식 모두 가능하도록 설계했다. `companion_applications`의 `(post_id, user_id)` 유니크 제약은 같은 사람이 두 번 확정되는 것을 별도로 막는다.

### 2.7 구역 만족도 집계 — zone_stats

평균을 계산해두는 대신 `rating_sum`과 `rating_count`를 함께 저장한다. 새 평가가 들어올 때 합계와 개수만 더하면 되므로 전체 재계산이 필요 없고, `rating_count`가 소표본 판정(5건 미만)에 그대로 쓰인다(REQ-F-305, REQ-F-110).

### 2.8 대화방을 별도 테이블로 두지 않는다

모집 글 1건에 대화방이 정확히 1개 대응하므로 `companion_rooms` 같은 중간 테이블을 만들지 않고
`companion_messages.companion_post_id` 로 직접 참조한다. 방을 따로 두면 "글은 있는데 방이 없는" 상태나
"방은 있는데 글이 삭제된" 상태가 만들어질 수 있다.

읽음 처리도 메시지마다 행을 쌓지 않고 `companion_message_reads` 에 **사용자별 마지막 읽은 시각**만 보관한다.
메시지 수 × 참여자 수만큼 행이 늘어나는 것을 피하고, 미읽음 개수는 그 시각 이후 메시지를 세어 구한다.

### 2.9 날씨는 경기와 기록 양쪽에 저장한다

`game_weather` 는 경기 단위 캐시이고, `attendance_logs.weather_sky` 는 기록 시점의 값이다.
같은 값을 두 곳에 두는 것처럼 보이지만 성격이 다르다.

기상청 단기예보는 **미래 예보**이므로 경기가 지나면 그 값을 다시 조회할 수 없다.
따라서 기록을 작성하는 시점에 값을 복사해두지 않으면 "비 오는 날 승률"(REQ-F-310)을 영원히 만들 수 없다.
`game_weather` 는 예보 조회용, `attendance_logs` 의 날씨 필드는 집계용이다.

### 2.10 탈퇴 처리 — REQ-F-007

`users.withdrawn_at`으로 논리 삭제하고 식별 정보를 파기한다. `attendance_logs`는 삭제하지 않는다. 삭제하면 `zone_stats`의 표본 수가 함께 줄어 구장 정보의 신뢰도가 떨어지기 때문이다. 후기 본문은 노출하지 않고 점수만 익명으로 집계에 남긴다.

## 3. 인덱스 설계

| 테이블 | 인덱스 | 목적 |
|---|---|---|
| attendance_logs | (user_id, game_id) UNIQUE | 중복 기록 차단 |
| attendance_logs | (user_id, created_at) | 내 기록 목록 조회 |
| attendance_logs | (stadium_zone_id) | 구역별 후기 조회 |
| games | (game_date) | 일자별 경기 조회 |
| games | (source, external_ref) UNIQUE | 외부 데이터 재수집 시 중복 적재 방지 |
| user_stats | (user_id, dimension, dimension_key, season_year) UNIQUE | 집계 항목 식별 및 upsert |
| companion_applications | (post_id, user_id) UNIQUE | 중복 지원 차단 |

## 4. 외부 데이터 반영 (REQ-F-107, REQ-N-013)

`games` 테이블의 `source` 컬럼으로 운영자 등록(MANUAL)과 외부 수집(EXTERNAL)을 구분한다. `(source, external_ref)` 유니크 제약을 두어 배치가 반복 실행되어도 같은 경기가 중복 적재되지 않는다. `collected_at`은 화면의 데이터 기준 시각 표시에 사용한다(REQ-F-106).

**팀 순위는 별도 테이블을 두지 않는다.** `games`의 결과로부터 승·무·패와 승률을 직접 산출한다(REQ-F-104). 외부에서 순위표를 가져오지 않기 때문에 원본 데이터만 있으면 파생 지표는 자체적으로 만들 수 있다.
