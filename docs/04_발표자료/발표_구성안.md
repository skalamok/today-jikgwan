## 강조할 지점

발표에서 다른 조와 갈리는 부분은 다음 세 가지다.

**1. 데이터 출처를 3단계로 검증했다 (8번 구간)**

| 단계 | 확인 | 결과 |
|---|---|---|
| 1. 이용약관 | KBO 제14조 차항 | 자동화 수집 및 타 플랫폼 연동 금지 |
| 2. robots.txt | KBO / STATIZ | 두 사이트 모두 `User-agent: *` 에 `Disallow: /` |
| 3. 권리자 문의 | STATIZ 운영자에게 메일 | 목적 무관 전면 거절 회신 수신 |
| 4. 대안 탐색 | TheSportsDB 공식 API | **약관상 이용 허용 확인 → 채택** |

막힌 데서 끝내지 않고 합법적인 대안을 찾아낸 것이 요점이다. 결과적으로 크롤링 없이 공식 API로 데이터를 확보했고, 외부 API 누락에 대비해 사용자 제보를 2차 출처로 두는 이중 구조까지 만들었다.

**슬라이드 구성 제안**: 왼쪽에 STATIZ 거절 회신 메일 캡처, 오른쪽에 TheSportsDB KBO 리그 페이지 캡처를 나란히 배치. 막힘과 해결이 한 장에 보인다.

**2. 소표본 문제를 설계에 반영했다 (5, 6번 구간)**
관람 2경기 2승을 승률 100%로 표시하면 통계적으로 오해를 유발한다. 표본 5경기 미만은 승률을 산출하지 않는 정책을 요구사항(REQ-F-305), 화면 설계, API 응답(`smallSample` 플래그), 데이터 모델(`rating_count`)에 일관되게 반영했다.

**3. 라이트 유저 문제를 구조로 풀었다 (3번 구간)**
기록이 쌓여야 가치가 생기는 서비스는 1년에 한두 번 가는 사용자에게 줄 것이 없다. 기록 작성 시 받는 구역 만족도 한 문항을 집계해 구장 정보로 되돌려주는 순환을 만들어, 라이트 유저는 소비자로 진입하고 헤비 유저는 생산자가 되는 구조를 설계했다.
